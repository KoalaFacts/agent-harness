# Proppi — project rules

Owner-controlled seed for the "Proppi 推进计划" scheduled task (repo ProppiAI/ProppiAI). The repo skill is `.claude/skills/advance-proppiai/SKILL.md`; if it is missing on main, the task's first PR creates it from this file (see `skills/autonomous-dev` §1). The task may make these rules stricter in its own skill, never looser.

References in the text below to B2–B12 point at the shared rules that now live in `skills/autonomous-dev` and `skills/verification-first`: B2 → §4 What counts, B3 → §5 authority, B4 → §1 Setup, B5 → §7 Ledger, B6 → §3 The loop, B7 → §6 Housekeeping, B8 → §5 Merge conditions, B9 → §9 Engineering defaults, B10 → §10 Report, B11 → §6 Docs discipline (and the section below), B12 → `verification-first` and §8.

## Docs files in this repo
docs/ROADMAP.md is the ledger only if it already exists on main; otherwise it is not created and the ledger is a "Roadmap" section of docs/product/one-stop-property-service.md. New steps extend existing design docs (decisions, build order, status) instead of adding new design docs; a design doc whose build order is fully shipped gets status implemented in place, and a fully superseded one is folded into its successor and deleted. Docs-file counts for B11 exclude the agent area owned by "ProppiAI-Agent 推进计划". Ledgers, evidence files, postmortems, dated proofs and migration headers are kept records. `.claude/rules/` is generated from .ai/rules and not counted.

## Verification boundary
this task installs both skills (`verify-proppiai`) on `proppi/verify-skills`; the repo is shared with "ProppiAI-Agent 推进计划", which adds the agent-area feature-map rows (MCP tools, widgets, the plugin package export) in its own PR — leave those rows to it. Because merging deploys production, the real boundary is the member app running locally against a local database (pglite or local Supabase) with console/mock providers, the landlord journey driven in headless Chromium, and the WhatsApp webhook exercised with recorded payloads through the console provider — never live sends or production data.

## Project

### P1 WHAT AND WHY
- Repo ProppiAI/ProppiAI (proppi.ai): a one-stop property service for self-managing landlords in New Zealand and Australia. The owner asked (2026-11-05) for proactive, autonomous development of the whole plan, not only WhatsApp; make ordinary product and engineering decisions yourself.
- Direction: docs/product/one-stop-property-service.md (approved 24 Oct 2026) and CLAUDE.md's positioning rules: never imply a service, channel, provider network or completion that does not exist; preparation, external execution and accepted completion are separate milestones; keep human approval and action-receipt boundaries. Design docs under docs/ (whatsapp-document-inbound-design.md, 2026-09-26-ai-workspace-ux-design.md, 2026-10-03-ask-ready-listing-design.md, fact-currency-design.md, listing-claim-check-design.md and others) carry decided designs and unfinished build orders.
- Repo docs and copy are en-NZ.
- Equivalent deliverable for B2: a merged PR, review findings fixed and pushed, or a new PR with a finished, tested step.

### P2 AUTHORITY SPECIFICS
- Branch prefix `proppi/` (housekeeping: `proppi/docs-cleanup-<yyyymmdd>-<slice>`); squash merge. Open-PR triage (autonomous-dev §3 step 0) covers every open PR except `agent/` branches (the other task's) and dependency bumps: never merge the postgres 4 Dependabot PR (#731) or any dependency bump (owner decision; report them). The separate "ProppiAI-Agent 推进计划" task works on `agent/` branches in the same repo: never touch its PRs or files it has open.
- Merging to main deploys to PRODUCTION through Vercel. Actions is billing-blocked (deploy-supabase does not run, CI checks do not start); the local gate is the evidence.

### P3 SETUP AND GATE
- Read CLAUDE.md, AGENTS.md, .ai/rules/* and the indices you need; follow them exactly (CQRS factories, DI boundaries, no ON DELETE CASCADE, branded IDs, no dead compatibility, en-NZ locale, full country/state names in public copy, tests that pin outcomes, abort/idempotency tests for pipeline handlers). Frontend work: .ai/frontend-patterns.md first.
- `npm ci --no-audit --no-fund`. LOCAL GATE before pushing: `node scripts/check-all.ts`, `npx vp check`, `npm run test:changed` (or named paths); for anything cross-cutting (migrations, Drizzle schema, server-core/agent-core contracts, bootstrap wiring, job transitions, shared UI primitives, auth) the full `npm run test` plus affected app builds; MDX changes need `npm run build -w @proppi/marketing`. Merge gate: `node scripts/check-all.ts`, `npx vp check`, full `npm run test`, `npm run build -w @proppi/member`, plus any other app the PR touches (docs-only PRs: check-all and vp check, plus the marketing build if MDX changed). The only allowed failure is one that also fails on origin/main without the PR; `scripts/proppi-agent/mcp-guidance.test.ts` currently does and must not be "fixed" by bumping its reviewed version.
- Before committing check `git status`; never commit regenerated artifacts (apps/agent/src/server/mcp/widgets/widget-build.generated.json, packages/templates/html/**, .next) — `git restore` them. If a change really alters the MCP tool surface, regenerate the catalog version (`npm run agent:catalog-version`) and review the connected workflow guidance in the same PR.
- A new migration: fresh UTC timestamp, IF NOT EXISTS, an index per FK, RLS on with no policy, the Drizzle mirror, and the pglite suites that load affected migrations apply it too.

### P4 LEDGER AND ORDER
- Ledger: per B11 — workstreams/milestones ordered by landlord value (one-stop request/work journey, property records and fact currency, prepared Work and listings, the AI assistant (MCP) surface, quality/reliability debt, documentation hygiene, the WhatsApp channel), each with ordered steps, acceptance criteria and a Status table.
- WhatsApp workstream (steps 1–7 on main, PR #732; step 8 waits on Meta business verification): W1 instant 👀 reaction to a text that starts a chat turn (closing texts keep their reactions); W2 quick-reply buttons (provider `sendButtons`, max 3, titles ≤20 chars, console provider logs only; webhook parsing of `interactive.button_reply`; opaque ids resolved server-side for the sender's own link; first use "🔁 Try again" through the same chat-turn path); W3 "✅ Correct" / "🏠 Change property" after a filed document via the owner-scoped document-to-property link command, properties as a list message (≤10 rows, app link beyond); W4 D3 notice to an unconnected number at most once per 24 h, persisting only a throttle keyed on a hash of the wa_id; W5 approve-by-reply through the same shared approval use case the app and MCP use, rechecking ownership and state; W6 proactive reminders behind configuration with approved templates and per-link opt-in (template approval and enabling are owner decisions).
- Choosing the next step: the highest-value step that is not done, not blocked, and can be finished and merged without the owner; rotate across workstreams; prefer no migration or only an additive one. When a workstream runs out, extend it from the product doc (requesting help, keeping related work together, who is acting and what is awaited, verifying the final result; then letting, ongoing management, maintenance, records/accounting support and selling as capability allows).
- Every PR updates the ledger's Status table, the design doc of the step (status, decisions, what remains) and the .ai indices when it adds or moves things.

### P5 PROJECT RULES
- Extra merge conditions: a PR is never merged in the run that opened it; Codex: if it has not reviewed the head and the PR is younger than 12 hours it waits, at 12 hours or more with no review merge on the gate alone and say so; migrations: any migration in the PR is already in production (check read-only with the Supabase MCP `list_migrations` on project svnegtetolkqtaodprde), otherwise it is "waiting for owner: apply migration <version>" with the exact SQL file named, and the run moves on.
- Production is read-only: no Supabase writes or migrations, no Vercel changes, no live Meta/WhatsApp, email, Trade Me or other external sends; development and tests stay in console/mock mode. No paid model, OCR, embedding, TTS or search APIs; no new paid dependency.
- Owner decisions (build behind configuration, mark blocked, move on): spending money, external accounts/registrations/Meta templates, legal/payment/dispatch commitments, production data changes.

### P6 HOUSEKEEPING SCOPE
- Each daily cleanup PR takes one coherent slice in rotation (docs/ design docs and plans; docs/product; .ai/ indices and rules; AGENTS.md/CLAUDE.md pointers; app/package READMEs), excluding the agent area that "ProppiAI-Agent 推进计划" owns (distributions/proppi-agent, apps/agent and packages/agent-core docs, scripts/proppi-agent docs, the agent section of the ledger, agent design docs). Fully shipped design docs get status implemented with PRs and code entry points; fully superseded ones are folded and deleted (no dead compatibility). Keep .ai/rules/* the single source of truth and regenerate `.claude/rules/` with `node scripts/sync-ai-rules.ts` when rules change. Weekly (Monday's first run) the cleanup is a whole-repo sweep: docs untouched for 60+ days are checked and fixed, marked implemented, or folded and deleted.

### P7 REPORT EXTRAS
- One status line per workstream (unchanged items at most one line); anything waiting for the owner with the exact action (e.g. which migration file to apply).
